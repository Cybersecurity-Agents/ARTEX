# R03 业务状态机与不变量

路线目标：先建设可重复的状态准备与动态依赖提取，使系统到达真实业务状态；在有独立规则时，再验证流程不变量。首版面向可重置的 Web/API 测试流程，使用[共用实验协议](共用实验协议与评估.md)。

复核定位：M3 交付 V1 可达性基础设施，M4 按规则来源验证 V2 反例能力。状态准备无需先证明业务规则，也不需要新控制器；两类收益分别评估。

## 从渗透测试逻辑推导

很多业务功能依赖前置对象、令牌和状态。直接请求后面的接口得到失败，可能只是因为没有创建对象、没有提交前一步或使用了过期标识；这并没有有效测试后续的业务边界。

渗透测试应先掌握一条正常成功流程，再提出规则明确的反例。例如受控文档必须提交并经审核后才能发布，就分别改变一个前置步骤、顺序或状态，并观察实际发布结果。

观察到某种正常顺序，并不能证明该顺序必须执行。只有业务要求、用户确认或灰盒规则能够支持必须遵守的约束；否则先记录异常候选，不将不同路径直接判为漏洞。

## 原设计已有能力与新增机制

现有 Planner 已能用待办串行派发依赖步骤，Worker 也可在自由探索中执行多请求操作。这解决了执行先后的一部分问题。

V1 显式保存被测业务的状态、请求间动态依赖和重置方法；V2 在此基础上接入有来源的安全不变量，构造可比较反例。调度意图的依赖与目标应用自身的业务状态，是两个层次。

相关接入见 [`agent/planner.go`](../../agent/planner.go)、[`agent/worker.go`](../../agent/worker.go) 和 [`traffic/traffic.go`](../../traffic/traffic.go)。

## 状态与不变量表达

| 记录 | 需要保存的内容 |
| --- | --- |
| 状态实例 | 测试主体、受控对象、实际状态字段或可观察业务事实 |
| 操作转换 | 前置状态、调用、动态数据来源、预期后置状态与证据 |
| 安全不变量 | V2 需要的规则、适用条件和独立来源；V1 不强制填写 |
| 重置配方 | 恢复干净状态所需的明确操作或环境快照 |
| 反例序列 | 相对正常序列改变的步骤及预期违规效果 |

正常流程只证明某些状态可达，不自动证明所有其他路径都不合法。异步任务需要独立的完成观察与等待上限；HTTP 200、请求已接收或界面提示成功不能替代实际后置状态。

例如规则可以是没有审核记录的受控文档不得进入已发布状态。实验判定器读取实际发布状态与审核关联，而不是只匹配发布接口的文本。

## 生成与执行流程

1. 从正常轨迹、文档或可用规格提取一条成功流程，验证动态标识的生产与消费关系。
2. 绑定主体、对象、实际后置状态和重置配方，重复到达该状态；正常流程登记到共用基线。V1 交付到这里即可。
3. 有独立规则时进入 V2，定义可观察的不变量，再研究一次跳步、局部换序或重复等变化。
4. 在干净且可比的状态运行对照与变体，按实际业务效果判定，不依赖单次响应码。
5. 无规则时保留可达状态及异常候选；无效前提只影响对应实验，不推断整个功能安全。

先限制深度和变更数量。前置资源创建失败时先修复依赖，不在其后追加大量必然无效请求；明确失败状态与无法观察后置效果也需要区分。

## 最小实现与接入

首版由人工确认一条小流程、参数依赖、可观察终态与重置配方。复用结构化 HTTP 执行器按真实响应提取对象标识，正常流程与 R02/R05 共用基线基础，保留每步观察及失败位置，不先建设通用业务建模平台。

接口规格可帮助生成请求，缺少规格时从实际成功轨迹开始。成功对照验证可达性，不能独立证明某顺序必须遵守。规则可以来自公开需求、用户确认或灰盒配置，不要求读取源码；完全没有规则来源时不自动判断业务违规，更不能由模型补写 OpenAPI 未声明的限制。

V2 以后再为已支持操作增加自动反例生成。会产生状态变化的版本需要可重置环境，发现写入不确定、异步未完成或恢复失败时停止后续对照，保留原因和记录。

## 分版本交付

| 版本 | 开发范围 | 验收产物 |
| --- | --- | --- |
| R03-V1 | 单流程、动态依赖、状态准备与重置，不要求业务不变量 | 可重复到达的真实状态、基线引用、无效依赖和复位夹具 |
| R03-V2 | 有来源不变量下的有限跳步、换序、重复及效果判定 | 正常与违规对照、规则缺失时保持候选、完整执行与准备成本 |
| R03-V3 | 主体和对象生命周期变化、与 R02 权限关系联动 | 跨条件流程记录、依赖失效后的重新准备、分支预算和组合评估 |

并发时序测试不作为 V1/V2 默认能力。若后续专门研究竞态，需要单独的可控调度、重复性和状态判定设计，不能用随机并发请求代替。

## 最小夹具

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| R03-A | 文档草稿、提交、审核、发布，提供正确规则与漏检前置两个版本 | 进入真实状态后验证不变量，识别漏检但不误报正确实现 |
| R03-B | 前一步创建对象失败，后续请求统一报错 | 判定依赖无效，不把未到达业务状态当完成测试 |
| R03-C | 合法的可选步骤和等价正常流程 | 没有规则要求的顺序差异不被判成漏洞 |
| R03-D | 异步状态更新与一次重置失败 | 依据真实后置状态判断；无法稳定对照时输出无法判定 |

## 有效性依据与失败条件

V1 按有效状态可达性、重复成功、动态依赖正确性和准备成本验收；V2 另外评估有来源规则下的违规检出、误报漏报与变体成本。两类收益分别报告，不能以序列长度作为深度指标。

业务规则来源不明时可继续提供状态准备，但停留在 V1，不升级违规结论。实际状态不可观察、重置存在残留或序列成本失控时，缩小支持流程，不能把失败的准备计为有效覆盖。

[RESTler](https://github.com/microsoft/restler-fuzzer)已实现请求生产消费依赖分析和状态化测试，可作为工程参考；[OWASP WSTG 的流程绕过测试](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/10-Business_Logic/06-Circumvention_of_Work_Flows/)说明业务规则与流程误用需要结合具体应用。ARTEX 的新增设计是由事实和轨迹驱动状态准备，以有来源的不变量作为判定器，再把结果反馈给持续探索。
