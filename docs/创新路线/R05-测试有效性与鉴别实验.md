# R05 测试有效性与鉴别实验

公共能力目标：区分没有测到目标条件与在有效条件下未复现，并用有预算的诊断恢复可判断状态。保留 R05 编号用于独立评估，建设形式调整为各路线共用的谓词、有效性与诊断模块，协议见[共用实验协议与评估](共用实验协议与评估.md)。

实施定位：M0 从轨迹审计和只读标注开始，M2 与 R02 首版共同贯通四道门。被动检查与主动鉴别分别交付、分别计量，不为本能力另建控制循环。

## 从渗透测试逻辑推导

收到拒绝或错误响应，不能直接解释成系统不存在漏洞。请求可能使用了过期会话、错误对象、无效业务状态，或者测试结果根本无法通过当前渠道观察。

一个有效的否定结论至少需要说明：正常请求仍可用，测试前提成立，实验方法适用，而且有能力看到它试图验证的效果。黑盒下无法确认的部分必须保持未知。

失败原因不明时，下一次请求应优先区分解释。例如用已知正常对象检查当前身份，再用对象拥有者检查对象是否存在，可以逐步区分会话问题、资源问题和权限拒绝。它比连续更换测试变体更有信息价值。

## 原设计已有能力与新增机制

[`agent/retester.go`](../../agent/retester.go) 已明确要求前提不足时输出 inconclusive，并要求正常对照才能判定 fixed；[`agent/planner.go`](../../agent/planner.go) 已要求复核弱否定结论。

新增机制是将这些原则推广成实验接口的可检查记录，在实际测试过程中维护有效性和原因候选，并让多个 Worker 按上下文版本共享有限的诊断结果。它不再仅依赖最后一轮自然语言总结来提醒模型。

机器检查必须使用注册的输入、观察要求与判定器版本；模型的原因标签只有建议权。单次状态码或模型填写 observed 不足以确认登录有效、方法成立或问题不存在。

## 判定与鉴别机制

| 内容 | 处理方式 |
| --- | --- |
| 实验前提 | 声明需要的身份、正常基线、对象状态、观察渠道与方法条件 |
| 实际证据 | 引用真实的对照与实验结果，检查上下文是否一致 |
| 失败解释 | 保存候选原因及支持证据，不能仅凭状态码唯一归因 |
| 下一次鉴别 | 选择能够区分候选原因、成本较低且在范围内的最小请求 |
| 最终结果 | 有效条件内形成结论；前提不足则无法判定，不写成安全或已修复 |

不需要伪造概率分布。V1 可以使用明确的原因集合、检查顺序与预期结果表；只有当某个观察真正排除了候选解释，才缩小集合。

## 关键检查逻辑

会话检查使用已知需要该身份、且语义结果明确的最小操作。公共健康页返回 200，只能支持传输层判断；登录页伪装成 200 不能证明身份有效。

对象不存在和无权访问可能都返回 404。应结合对象拥有者的有效对照区分；仍无法区分时保留多个原因，不推断权限实现细节。

正常对照可以在实验批次前后、会话或状态变化时执行，并缓存到对应上下文版本。缓存不能跨主体、租户和不相容状态复用，也不能因为短时间内请求相似就认定同样有效。

服务端可能在没有本地版本事件时撤销会话或改变状态，因此缓存还要有复查期限和异常失效规则。同一上下文编号不代表健康状态可以无限复用；期限与复查成本在夹具中确定。

会话健康、R02 的拥有者对照、R03 的正常流程统一使用公共基线的存储、引用和失效机制，各自保留用途、条件和判定器，不相互替代，也不重复保存三套原始观察。诊断请求仍沿现有派发、领取与授权路径执行，准备成本不能隐藏在基线子系统中。

实验后正常功能突然失效，可能是环境变化，也可能是本次触发的真实缺陷。保留该变化为独立线索；当前实验先暂停下结论，再在可重置环境中判断原因，不能把它一概当作噪声丢弃。

缺少回显或外部观测渠道的实验不自动得到否定结论。黑盒检查只声明所能证实的有效性层次，不能声称已经到达某个内部代码分支。

## 最小实现与接入

先从已保存的执行轨迹读取正常对照、错误和总结，形成结构化标注，与独立评估结果比较。V1 不产生目标请求，不拦截已有自由探索。

V2 为实验接口提供前提声明、公共谓词、基线引用和鉴别预算，结果经过写回门进入既有事实与证据路径。无法修复前提时返回明确阻塞原因，不无限刷新登录、重试网络或重复创建对象。

随每项检查器交付门决定及报告样例，展示当前结论资格、失效原因和未检查条件。新实验四值结果通过适配呈现，不直接替换现有复测三值 verdict。自动判定权限按谓词类型晋级，不能因 R05 整体开启就信任全部诊断规则。

接入点为 [`agent/worker.go`](../../agent/worker.go)、[`agent/tools.go`](../../agent/tools.go)、[`server/engine.go`](../../server/engine.go) 和现有执行记录；参考独立复测的结论边界。此机制不覆盖未接入实验协议的任意工具调用。

## 分版本交付

| 版本 | 开发范围 | 验收产物 |
| --- | --- | --- |
| R05-V1 | 轨迹审计、前提表、谓词契约、候选原因与反例 | 可判与缺失样本分开；只观察，不宣称实际执行节省 |
| R05-V2 | 公共有效性谓词、基线与有预算的鉴别实验 | 分别验证被动检查和主动恢复，交付门日志与报告，记录全部额外请求 |
| R05-V3 | 多 Worker 复用健康状态，按上下文变化失效 | 并发与状态漂移夹具、缓存边界、重复诊断减少的对照结果 |

## 最小夹具

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| R05-A | 过期会话返回带相似页面结构的 200 | 识别正常对照不成立，不输出未发现或已修复 |
| R05-B | 对象不存在与正常权限拒绝都返回 404 | 通过受控拥有者对照区分，证据不足时保留未知 |
| R05-C | 实验前正常，实验后发生状态污染或服务异常 | 记录变化与独立线索，停止使用失效基线解释后续结果 |
| R05-D | 操作可能有效但现有渠道无法观察效果 | 输出无法判定，避免把无回显当作不存在效果 |

## 有效性依据与失败条件

主要收益是减少无效实验被误记为安全结论，并尽快恢复可判断的测试条件。必须同时考察真正问题的检出、可判定比例和额外成本，不能靠把所有结果都标为无法判定取得漂亮的误报数据。

如果正常对照与漏洞测试需要的身份或状态并不相容，或者诊断循环消耗更多预算却没有恢复有效测试，则限制该检查器适用范围，退回建议模式。

[RESTler 的 FAQ](https://github.com/microsoft/restler-fuzzer/blob/main/docs/user-guide/FAQ.md)记录了测试期间认证或后端状态异常导致大量请求失效的问题，支持持续检查有效性这一动机。[AuthMatrix 的说明](https://github.com/SecurityInnovation/AuthMatrix)也将无效会话列为可能误报的来源。二者支持失败机制的真实性；自主鉴别流程的收益由 ARTEX 夹具和配对实验验证。
