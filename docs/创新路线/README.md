# ARTEX 创新路线与版本规划

创建日期：2026-10-15。复核更新：2026-10-16。源码基线：a9d11cb。状态：研发设计，所有版本与夹具均为后续开发计划。

实施主线是先审计，再加固现有循环，建设派发、领取、写回、完成四道门；能力路线沿现有双图与 Planner/Worker 接入。R05 下沉公共谓词、基线与诊断能力，R02 首先验证，R03 先交付可达性，R01 和 R06 随依据与复测建设，R04 后置。

这里的创新指相对 ARTEX 当前实现的增量设计。授权差分、状态化测试、假设维护和输入约简均有成熟研究或工具基础。新增价值在于将它们接入自主探索循环，并保留身份、对象、状态、证据及适用条件，不主张行业首创，也不把来源项目的效果当作 ARTEX 的实测结果。

保留 R01—R06 编号用于研究与评估，不再将它们理解为六套独立基础设施。修订后的[问题驱动的实验搜索架构](../问题驱动的实验搜索架构.md)以门化 Planner 为主交付物，独立控制器仅在残余调度问题满足准入条件后研发。

## 六条路线

| 路线 | 具体创新 | 为什么值得做 | 明确前提 |
| --- | --- | --- | --- |
| [R01 条件化假设与计划修订](R01-条件化假设与计划修订.md) | 把结论的适用条件和计划依据显式关联，按反证定位受影响方向 | 防止一次局部失败封死整条路线，也防止旧假设持续消耗预算 | 能识别关键上下文差异，并拥有真实依据引用 |
| [R02 身份与对象关系差分](R02-身份与对象关系差分.md) | 根据所有权、角色和租户关系选取少量高价值授权对照 | 用受控对象和明确权限预期验证边界，减少盲猜对象与状态码误判 | 有授权测试身份、对象关系与独立的权限预期 |
| [R03 业务状态机与不变量](R03-业务状态机与不变量.md) | 先建设状态准备与依赖提取，再按有来源规则生成反例 | 提高有效状态可达性，规则明确后再判定业务违规 | V1 需要可重复流程与可观察状态；违规判定另需独立规则 |
| [R04 证据约束的能力链](R04-证据约束的能力链.md) | 用带主体、对象、条件的已证能力拼接路线，只补测缺失前提 | 降低把多个发现串成虚构利用链的风险，提高已有发现的组合价值 | 能力具有可检查证据，组合中的身份与资源条件相容 |
| [R05 测试有效性与鉴别实验](R05-测试有效性与鉴别实验.md) | 向所有路线提供公共有效性谓词与基线，单独评估主动诊断策略 | 避免登录失效、对象不存在和环境异常被写成安全结论 | 有适用对照或可信观测；谓词逐项验证后获得判定权 |
| [R06 保持对照的最小复现](R06-保持对照的最小复现.md) | 在保留权限关系和漏洞效果的条件下约简请求与序列，生成可重复检查 | 降低偶然响应和冗余步骤对复现、修复确认的干扰 | 有明确判定器、可重复环境和必要的重置手段 |

能力边界是：R05 判断一次实验是否成立，R01 管理结论跨轮复用的条件；R02 验证主体与对象的权限关系，R03 准备业务状态并在有规则时验证流程；R04 组合已有能力，R06 约简已有证明。它们共享基础记录，各自保留判定职责。

## 有效性判断与优先级

优先考虑能够直接纠正具体测试错误、且能够在小夹具中验证的路线。R05 针对无效测试，R02 针对权限关系，R03 针对业务状态，R01 针对条件错误外推，R06 针对复现条件丢失。它们的收益机制都可以逐项观察，不依赖先训练新的大模型。

R04 对事实质量和规则完整性的要求更高，作为后续组合路线。它的目标是提高可执行链的比例，不能仅以生成了更多图上路径作为成功。

| 推进定位 | 路线 | 主要收益指标 | 主要风险 |
| --- | --- | --- | --- |
| M0 观察、M2 公共基础 | R05 | 无效测试被误记为安全结论的次数、诊断恢复成本 | 过严校验导致大量无法判定，挤占真正测试预算 |
| M2 第一项贯通能力 | R02 | 已知策略下的授权边界检出、误报和全部准备成本 | 错误推断权限预期，混用身份或把共享对象当私有对象 |
| M3 可达性、M4 规则反例 | R03 | 有效状态可达性；有来源规则下的违规检出 | 把观察到的流程误当强制规则，重置不完整 |
| 前期观察，M3 完整修订 | R01 | 依据变化后的错误续派、合理重开与重复开销 | 相似条件匹配错误，产生反复重开或错误剪枝 |
| 随 M3 复测推进 | R06 | 新环境复现成功、保真约简程度、交接成本 | 判定器过弱，约简后证明了不同问题 |
| M4 后置组合验证 | R04 | 经验证可执行链的比例、补齐关键前提的成本 | 将不同主体、不同对象或不同时刻的能力错误拼接 |

这是基于机制和项目适配性的优先判断。只有达到各路线的验证门槛，才能进入自动执行；不预设成功率提升百分比。

## 相对现有设计的区别

现有 Planner 已会要求复核弱否定结论，利用 TodoWrite 分步推进串行链；Worker 已能检索其他执行过程；独立漏洞复测已要求有效前提与正常对照；事实已包含 observed/inferred 置信度。这些能力不重复计为创新。

能力方向补充的是可执行的实验表达与检查：将上下文、断言和证据绑定成稳定记录，按这些记录生成对照、检查适用性、修订计划和组合能力。模型负责提出策略与解释语义；已注册且通过验证的机器谓词才有相应准入和升级权。`observed` 标签、节点 `confirmed` 或资产触达覆盖率均不能替代证据验收。

## 共用协议与研发边界

全部路线使用[共用实验协议与评估](共用实验协议与评估.md)。先统一最小上下文、实验与断言的含义，避免六条路线各建一套结论系统。原始输出仍由执行记录、流量和证据设施保存，图中保存引用与结论，不复制六份正文。

图事务、完成权限和规划引用 schema 见[架构复核与演进设计](../架构复核与演进设计.md)。离线观察可以前期开展；自动执行前必须通过相应的可靠性与谓词验收。公共基线统一存储、版本和复查机制，健康、拥有者对照和正常流程仍分别判定。

路线保留关闭、观察、建议、执行四种模式；谓词按类型另设观察、建议和强制检查的权限阶段。路线开关不关闭基础引用、事务和完成权限规则。观察模式不产生目标请求；尚不支持的场景保持未知，开放探索仍然可用。

## 路线内版本

V1、V2、V3 是每条路线内部的研发里程碑，不代表 ARTEX 已发布的版本号。

| 路线 | V1 最小验证 | V2 可执行能力 | V3 融入持续探索 |
| --- | --- | --- | --- |
| R01 | 手工标注关键依据，观察条件变化与受影响计划 | 持久化依据版本，复用触发器与恢复扫描实施复核 | 条件化负结果与受控重开 |
| R02 | 两个身份与受控对象的只读差分 | 角色、租户与动态对象关系 | 关联流程并输出下一步验证建议 |
| R03 | 一条真实成功流程、依赖提取与状态准备 | 有来源不变量下的有限跳步、换序与重复实验 | 跨身份和对象的流程组合 |
| R04 | 手工整理已证能力，检查组合相容性 | 为单个缺失前提生成验证任务 | 增量修订与多事实组合 |
| R05 公共能力 | 对历史轨迹标注有效性，形成谓词契约 | 共用基线、前提检查与有预算的诊断 | 跨 Worker 共享有版本与期限的诊断状态 |
| R06 | 锁定不可删除的证明条件，产生约简候选 | 在可重置环境中保真约简 | 接入独立复测与回归记录 |

## 实施顺序与阶段验收

M0—M4 是主线顺序，不是发布版本或工期承诺。阶段内可开展只读夹具验证，涉及真实执行和结论升级的交付按依赖晋级。

| 里程碑 | 实施内容 | 必需交付与验收 |
| --- | --- | --- |
| M0 最先审计 | 目标证明、否定复核、重复工作、图与恢复错误分类；开展 R05-V1、R01-V1 的离线观察 | 样本清单、可用性与统计口径、成本基线和夹具；数据不足明确标记，不虚报发生率 |
| M1 可靠性加固 | 完成旁路保护；关键图事务、错误传播、不变量与启动对账；计划依据及预期产出引用 schema、版本与恢复 | 工具配置回退不能恢复纯 reason 完成权；连边故障不留部分成功；重建后计划可恢复，迟到写入被拒 |
| M2 主交付物 | 公共观察、机器谓词、基线与结构化 HTTP 通道；R05-V2 和 R02-V1 贯通四道门；决策日志与分级呈现同步交付 | 识别会话失效、合法拒绝、合法共享及实际违规；派发后前提变化可在领取及关键动作前发现；未知规则不自动证明目标 |
| M3 能力扩展 | R02-V2；R03-V1 状态可达性；R01-V2 持久复核；R06-V1/V2 随独立复测接入 | 动态依赖与重置可重复；依据变化不错误续派；约简保持原对照和证明关系，准备及诊断成本入账 |
| M4 分别晋级 | 有规则来源时做 R03-V2；分别验证各路线 V3；基础满足后最后推进 R04-V1，再按结果做 V2/V3 | 规则不靠模型猜测；跨轮收益有独立对照；能力链逐步走通，不能用图上路径数量验收 |

M2 的依据版本检查先限定显式引用，不以 R01 的全量语义冲突识别为前置条件。R03-V1 无需先有业务不变量，只有违规判定阶段才要求独立规则；R06 不等待 R01 全部完成。R04 可使用人工审核能力记录独立验证，但不先开发通用链路搜索平台。

公共基础与路线能力保持一份状态来源，图中引用原始记录。新增门应覆盖共用业务路径，并明确通用工具尚未纳入的检查范围。任意 Bash 不能被默认算作结构化 HTTP 适配器已覆盖的执行。

## 新控制器的条件分支

独立控制器不列为 M0—M4 的必经交付。它的最早准入前提是拟研究任务类型已通过 M1、M2，且仍有可重复的全局调度失败：当时存在可用替代候选，记录足以归因，并已比较阶段配额、优先级与依赖唤醒等小改动。

满足前提后，先登记样本、重复次数、主指标、允许退化和总成本上限，再进入 A2 受控独立控制原型。采用前必须证明相对完整门化 Planner 的增量，并在保留任务中复核；未达到则继续使用主线。具体案例、排除条件和 A2/A3 验收见[控制器准入](../问题驱动的实验搜索架构.md#什么时候才需要新控制器)。

四组评估为 E0 原实现、E1 M1 加固、E2 门化 Planner、E3 同能力的独立控制器。前两组区分基础收益，E2 是主交付物，E3 与 E2 只改变选择权与预算分配，不增加账号、隐藏规则或总预算。门槛数值根据审计和成本确定，在评估前固定；未登记或样本不足时只作观察。

## 每个版本应交付的内容

每次迭代交付字段契约、输入输出示例、支持边界、固定夹具、门决定和报告样例、配对评估记录、开关及回退方式。评估分别报告误报、漏报、错误完成、无法判定、准备请求与模型成本，禁止只以意图数、请求数或图节点数作为收益。

目标已达成、预算耗尽、前提阻塞、阶段收益不足和人工停止分别交付终止原因。简单预算和边际推进规则先在现有循环验证；停止不等于目标完成，也不以现有粗略覆盖率证明已经测透。

未通过门槛的版本保留为观察或建议能力。先修正判定器、上下文或前提表达，再决定是否扩大自动执行范围。
