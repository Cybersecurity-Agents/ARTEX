# ARTEX 架构复核与演进设计

创建日期：2026-10-15。复核更新：2026-10-16。代码基线：`a9d11cb`。状态：研发设计，新增机制尚未实施。

ARTEX 的主线保留双图、Planner 与 Worker 分工，以及 Go 单体和 PostgreSQL 主体。先审计已有轨迹，再修复完成权限、图写入和规划恢复，随后在现有循环中建设派发、领取、写回、完成四道门及公共实验协议。

独立搜索控制器不作为首批交付物。问题、观察、依据和版本先由现有 Planner 使用；只有门化后仍出现可重复且无法用较小修改解决的全局调度失败，才进入独立控制原型。完整准入条件见[问题驱动的实验搜索架构](问题驱动的实验搜索架构.md)。

能力建设按[创新路线与版本规划](创新路线/README.md)推进。R05 下沉公共检查与诊断，R02 优先，R03 先做状态可达性，R01 复用现有唤醒机制，R06 随复测推进，R04 后置。各版本均需验证收益，不能提前承诺成功率提升。

## 现有架构与设计价值

ARTEX 已经形成持续探索的基本循环：用户给出目标，Planner 根据已有事实选择方向，Worker 执行一条明确的意图，将资产、事实、漏洞和执行记录写回，Planner 再据此调整下一步。

| 现有机制 | 职责与价值 |
| --- | --- |
| 资产图 | 保存共享资产及其关联，回答发现了什么、资产之间有什么关系 |
| 探索图 | 用目标、意图、事实、漏洞和提示及其关系记录探索来源、过程和结果 |
| Planner | 综合目标与全局态势，维护跨轮待办，决定下一步探索方向 |
| Worker | 一次执行一条意图，积累证据，并把执行中发现的新线索交回 Planner |
| 过程检索与会话记录 | 复用其他 Worker 的过程观察，支持继续执行与追查问题 |
| 冷热压缩与摘要 | 在保留原始节点的基础上管理上下文体积 |
| 证据与复测能力 | 已有漏洞证据快照、证据版本及独立复测路径 |

双图、事实驱动规划、过程信息交换和多轮待办均是原设计的能力。后续方案应在这些机制上增量演进，保留开放探索和跨资产联想。

## 已确认的可靠性缺口

### 完成判定缺少共同的证据验收

[`agent/tools.go`](../agent/tools.go) 的 `proveGoal` 检查目标与证据节点的归属、可读来源和类型，未检验证据充分性、条件有效性或量化验收；证明关系与目标状态的写入错误也被忽略。

`goal_met` 的处理函数可以直接设置任务完成，但不能据此认定默认 Planner 一定能调用它。[`agent/toolcatalog.go`](../agent/toolcatalog.go) 已默认解绑该工具，[`server/orchestration.go`](../server/orchestration.go) 有旧库解绑迁移。残余风险包括手工重绑，以及 [`server/assembly.go`](../server/assembly.go) 读取工具表失败后放行基础工具集。完成权限应由共同验收规则保护，不能只靠工具可见性控制。

`confidence=observed` 当前由模型填写，`confirmed` 是节点工作流状态，二者都不能单独充当程序验证结果。现有覆盖率也只是粗略资产指标：[`db/task_assets_context.go`](../db/task_assets_context.go) 将关联 fact 的资产计为已测，不等于这些资产已完成系统性验证。量化目标须先定义指标口径与版本，再由程序计算。

### 规划状态依赖 Planner 实例

[`agent/planner.go`](../agent/planner.go) 的 `todos` 是内存 map，`todoFor` 让同一个 Planner 实例中的多轮规划共享待办，`NewPlanner` 则创建空 map。这里的跨轮保留不等于跨实例持久化。

[`server/task_llm.go`](../server/task_llm.go) 的 `invalidateTaskAgents` 清空 Agent 缓存，后续 `agentsForTask` 会重新创建 Planner。因此，进程重启和 Agent 缓存失效后的重建都会中断这份内存待办的连续性。

规划状态应归属于任务，独立于模型会话和 Planner 对象的生命周期。旧实例仍在运行时，还需要防止其迟到写入覆盖新的规划版本。

### 部分图操作存在分步提交窗口

[`agent/tools.go`](../agent/tools.go) 存在以下路径：

- 创建意图后单独写入来源关系，并忽略 `Link` 错误。
- 创建事实后单独写入 `intent → yields → fact` 关系，并忽略连边错误。
- 证明目标时分别写入 `proves` 关系和 `met` 状态，并忽略两个写入错误。

这些路径可能在数据库操作失败时留下部分成功的结果，例如意图缺少来源关系，或者目标已经标记完成但证明关系没有保存。

项目并非缺少事务能力。[`db/finding_traffic.go`](../db/finding_traffic.go) 的 `RecordFindingTx` 已将漏洞节点、意图关系和相关记录纳入事务。应将这种业务事务边界推广到其他关键图操作。

### 观察条件在汇总阶段可能丢失

`record_fact` 的工具说明要求模型尽量汇总一次探索的多个观察，并非数据库自动合并。当前字段没有独立的观察级上下文引用，身份、对象和状态差异可能在总结时丢失，事后增加 schema 不能恢复已经省略的信息。

受支持执行器应先保存原始观察与上下文，再生成 fact 摘要。摘要可以粗粒度，断言的适用条件及各条观察不能被压成一个无条件结论。

### 领取和通知尚未表达持久依赖

[`server/engine.go`](../server/engine.go) 的 `claimNext` 调用 [`db/exploration.go`](../db/exploration.go) 的 `ClaimIntent`，目前只原子检查意图为 open 并领取，没有前提版本检查。

[`server/manager.go`](../server/manager.go) 已有 `TriggerEvent` 和 debounce 唤醒所需的事件提示，但 `pendingTriggers` 保存在内存。它们可以复用来通知变化，不能代替持久的依据状态、复核待办和恢复扫描。

## 最先开展的轨迹审计

M0 先确定实际可用的 transcript、activity、图关系和配置版本。检查调用记录是否完整、工具当时是否可达、任务和意图能否关联；资料缺失的样本标为不可判，不把工具定义存在当作实际调用证据。

| 审计对象 | 核查内容 | 影响的优先级 |
| --- | --- | --- |
| 目标完成 | 实际 `prove_goal` / `goal_met` 调用、证据链、条件及验收；推断事实参与证明的情况 | 完成门、证据适配与旁路保护 |
| 否定观察 | 当时对照是否有效，是否计划并实际执行复核，复核后是否仍错误外推 | R05 公共检查、R01 条件复用 |
| 调度与预算 | 重复死路、准备和诊断成本、探索与证明等待、可用替代候选 | 简单配额、停止规则及控制器是否有必要 |
| 图与恢复 | 必需关系缺失、部分写入、待办重建、迟到结果与未知动作 | 原子操作、引用 schema、启动对账 |

比例按可判样本定义分母，分别报告完整、缺失和无法归因的数据。`inferred` 占比只作线索，仍需区分有依据的推导与证据不足。人工或模型审阅应保留原始引用；模型意见不能自动充当真值标签。

审计交付样本清单、错误分类、脱敏引用、统计口径和下一阶段优先级。历史记录不足时先补必要观测与受控夹具，不虚构历史发生率，也不预设一天即可完成。审计与准备性修复可以衔接，但不能跳过基线后宣称收益。

## M1 基础加固

本阶段先修复可靠性和明显的完成旁路。M2 再接入具备明确证据语义的谓词与四道门，不将“事务提交成功”当作目标已被证明。

### 完成权限收敛

取消模型仅凭 reason 自动结束任务的能力；若保留 `goal_met` 名称，其处理函数也必须转入共同验收路径。高权工具在工具表读取失败时不能因回退而重新获得完成权限。

`prove_goal` 只有在必要写入成功、证据引用有效且满足当前支持的验收规则后才能升级目标。尚不支持的语义目标保留待验收状态，由明确的人工确认流程处理；模型提供证据候选和理由，不能自行补成已验证规则。

目标完成与停止探索分开。超时、预算耗尽、前提阻塞或阶段收益不足应交付部分结果与原因，不标为目标达成。

### 原子的图领域操作

围绕以下业务动作组织数据库事务：

| 业务动作 | 一起提交的内容 |
| --- | --- |
| 创建意图 | 意图节点、资产锚点和必要的来源关系 |
| 记录事实 | 事实节点、资产锚点和对应的产出关系 |
| 证明目标 | 经校验的证据引用、证明关系和目标状态变更 |
| 创建目标 | 目标节点及任务根的必要来源关系 |

事务内校验节点归属、关联任务引用权限、状态和必要关系；事务提交成功后再返回成功并触发后续通知。外部命令不应包含在长数据库事务中。

`agent/tools.go` 当前五处忽略 `Link` 错误，包含意图父关系、根关系、目标证明、事实产出和目标来源。围绕业务动作推广事务与错误传播，增加必要图关系的不变量检查及启动对账。允许的直接来源任务引用要显式识别，不能将合法跨任务证据误判成孤儿；无法可靠修复的记录进入人工核查，不自动删除或猜测补边。

这里增加的是现有存储层的业务操作边界。数据库继续作为业务状态的权威来源，暂不增加平行的状态内核或完整事件溯源平台。目标证明的语义充分性仍需要按目标定义验收方法，事务只能保证记录一致。

### 任务级规划状态

将待办、规划版本和必要的依据引用保存到任务所属的持久化记录中。Planner 每轮从记录恢复，成功更新待办时保存新版本，写入时检查预期版本，拒绝过期覆盖。

这不是简单把内存 map 序列化。先为计划步骤设计稳定标识、依据引用、预期产出引用及绑定方式：尚未产生的事实使用计划内输出占位引用，实际产出后绑定观察或断言。执行进度从有效产出和运行状态派生，模型的勾选保留为便签，不能独立证明步骤完成。

待办仍是可修订的计划草稿。只有已经明确的前置条件才作为调度约束，不要求预先生成完整流程。历史待办没有的依据保留未知，不用模型猜测补齐。

恢复计划不代表可以安全重放所有外部命令。一次工具执行可能已经产生效果，但结果尚未保存；恢复时应结合执行记录和外部状态判断下一步。

### 统一证据引用与不确定性表达

现有 `record_fact` 已支持 `evidence` 和 `confidence`，区分 `observed` 与 `inferred`；`graph_overview` 也会携带置信度，包括关联任务的事实概览。不能将这项已有能力重新包装为新增设计。具体实现见 [`agent/tools.go`](../agent/tools.go)。

增量工作是让重要结论拥有稳定的来源引用，例如工具调用、执行记录、原始输出或证据快照，并让置信度贯穿摘要、检索和目标评估。节点的 `confirmed` 工作流状态不应被解释为所有内容都已独立复现。

`confidence` 继续表达直接观察还是推断；复测则另外记录方法、条件与结果。HTTP 快照可以复用现有证据设施，命令输出和非 HTTP 证据也应有适当的引用方式，不强制所有结论绑定 HTTP 流量。

验证方式按目标选择：程序检查已实现的条件，需要复现时调用复测能力；开放语义由模型提出候选、人工明确验收。多个真实观察可以通过有来源的推导规则支持结论，不将 `inferred` 全部视为无效，也不将 `observed` 标签视为充分条件。

### 执行标识与评估基线

为执行增加稳定的运行标识和尝试编号，并记录实际使用的模型、提示词与工具配置版本、压缩策略及预算。记录配置摘要，不保存密钥；允许故障切换，同时保留每次调用的实际选择。

评估与首轮改造同步开展。先用受控案例和保存的执行轨迹建立基线，关注恢复正确性、重复操作、证据充分性、目标判定和单位有效产出的成本。LLM 输出存在波动，比较时应固定任务条件，并重复运行观察分布。

## M2 在原循环中建立四道门

派发、领取、写回和完成使用共用领域操作，覆盖 Agent、平台工具及人工投递涉及的相同业务约束。完成门不能因工具重绑绕过，领取门不能只看派发时的版本，写回门必须保留观察条件。具体职责见[主架构中的四道门](问题驱动的实验搜索架构.md#四道门的职责)。

公共基础先提供观察明细、机器谓词注册、上下文与用途隔离的基线，以及结构化 HTTP 执行通道。R05 的检查与诊断接入这里，R02 首版作为贯穿四道门的最小能力。封闭词表只约束自动判定，模型仍能提出开放探索方向。

门决策日志、实验结果和证据分级展示与检查器同步交付。现有 [`web/src/components/finding-retest-panel.tsx`](../web/src/components/finding-retest-panel.tsx) 已展示“仍可复现、已修复、无法确认”，应复用扩展；新增四值实验结果不直接替换现有复测 verdict。

路线开关和谓词晋级分别控制，引用归属、事务及完成权限等基础规则始终适用。尚未支持的动作明确边界，不能宣称任意 Bash 已获得完整的前提和作用范围检查。

## 对原八项建议的调整

| 初始方向 | 复核后的取舍 | 推进条件 |
| --- | --- | --- |
| 任务内核与结构化计划 | 收敛为原子的领域操作、计划引用 schema 和持久化规划状态 | M1 处理；独立控制器需另外满足准入条件 |
| 持久化执行与租约 | 先记录运行标识、尝试与恢复依据 | 多实例或远程执行时再引入租约 |
| 观察事实验证三层 | 扩展现有事实、置信度和证据设施 | 避免重复存储三套相似记录 |
| 统一上下文编译 | 先优化全局摘要、局部细节和按需读取 | 用信息遗漏与成本数据验证收益 |
| 完整覆盖矩阵 | 先记录实际测试条件、依据、结果与证据 | 系统性覆盖任务再生成针对性矩阵 |
| 自适应调度 | 先建设预算台账、阶段配额与有原因的停止 | 复杂选择器需证明门化后仍有全局调度失控 |
| 多种 Runner | 保留轻量执行接口，按需接入容器或远程环境 | 有明确隔离或部署需求时推进 |
| 配置记录评估与依赖注入 | 评估前移；依赖注入围绕具体测试难点实施 | 不进行缺少目标的整体重构 |

完整计划引擎、图数据库、常驻裁判 Agent、RAG 服务和分布式工作流框架均不作为首轮的默认依赖。

## 保留自主探索的设计边界

### 全局摘要与局部证据结合

Worker 的上下文采用小型全局概况、当前意图的相关子图和按需读取的详细记录。已有冷热压缩和过程检索继续承担相应职责。

[`agent/worker.go`](../agent/worker.go) 的 `renderWorkerGraphOverview` 明确鼓励 Worker 在执行本意图时发现跨资产线索，并将其交给 Planner。上下文裁剪应保留这种联想能力；Worker 发现新方向后交接线索，实际执行仍由 Planner 分配。

### 去重与停止判断保留条件信息

硬去重主要处理同一次提交的重复执行。语义相似可以提醒 Planner，但相同资产或相似描述不足以判定重复：身份、参数、环境、时间及事实依据改变后，再次测试可能有价值。

没有新增事实可以触发重新评估方向，但不单独触发终止。按预先登记的窗口与成本限制检查边际推进，允许在有限替代策略后停止探索；基础设施阻塞、假设未复现、预算耗尽与阶段收益不足分别记录，不把停止解释为已经测透或目标完成。

### 测试记录与覆盖率保持准确含义

资产被触达、执行过某项测试和完成系统性安全验证，是不同层次的指标。现有粗粒度覆盖信号应按其实际含义展示。

优先保存实际发生的测试及条件，按需要查看缺口。避免默认展开资产、身份、操作、假设和环境的全部组合，使调度被大量低价值条目占满。

### 授权边界独立于发现范围

[`db/task_scope.go`](../db/task_scope.go) 的 `AddAutoScope` 会根据登记资产增加域名或 IP 范围，[`agent/tools_insert.go`](../agent/tools_insert.go) 会调用该路径。因此，动态增长的 `task_scope` 不宜直接作为固定的执行授权边界。

若增加执行权限控制，应单独保存由用户管理、带版本的授权范围，按所需粒度表达主机、IP、端口等条件。发现新资产可以扩展知识与任务范围记录，不能自动扩大执行授权。现有资产拦截机制仍需结合实际动作目标来确定覆盖边界。

### 租约与外部副作用分别处理

单进程部署先明确运行所有权。多实例或远程 Worker 场景再设计领取、续租、回收和拒收过期 Worker 写入的规则。

租约过期不能撤销已发出的命令，也不能保证外部操作只执行一次。已开始但结果未知的动作，需要根据动作性质使用幂等标识或查询外部状态后再决定是否重试。[LangGraph 的幂等性说明](https://docs.langchain.com/oss/python/langgraph/functional-api#idempotency)同样指出，未完成的任务在恢复时可能再次执行，需要处理重复副作用。

## 可证伪计划的创新方向

### 相对原设计的增量

原探索图已经通过 `derived_from` 等关系记录事实与意图的来源。新的方向是在这些来源关系上进一步表达：计划依赖哪个假设、假设适用的条件是什么、哪些证据支持或反驳它，以及计划依据的是哪个版本。

这样，系统除了保存探索历史，还能在依据变化后定位需要重新评估的计划。关键增量是依据有效性的维护，以及对受影响计划的显式复核。

### 最小表达与修订流程

先对关键探索方向记录以下信息，不要求每个操作都填写完整结构：

| 信息 | 用途 |
| --- | --- |
| 假设与适用条件 | 说明判断内容，以及适用的资产、身份和环境 |
| 支持证据 | 引用实际观察，保留来源与不确定性 |
| 预期观察与反证条件 | 说明测试想得到什么，什么结果会削弱当前依据 |
| 依赖该假设的计划 | 定位依据变化后需要复核的待办或意图 |
| 依据版本与复核状态 | 区分原计划、待复核计划与修订后的计划 |

可以先通过现有事实、提示和计划关联记录表达，确认有收益后再考虑新增节点或边类型，不默认建立第三张图。

新证据进入后，先检查它是否适用于相同条件。模型提出疑似冲突时登记复核候选；机器规则确认必要依据失效或未知，或人工明确决定时，再进入阻断性复核。向 Planner 提供支持与反驳证据，由其在共同约束内修订计划，保存原因和历史版本。

状态先持久化，再通过现有触发与 debounce 通知；恢复时扫描未完成复核。机器已确认前提失效时，Planner 不能只修改文字标签使其重新通过；新的有效依据应走共同写回和准入路径。

语义冲突不会仅凭一个分类标签自动撤销整条链路。目标的完成依据受到影响时，也应触发复核；重评估不等于删除历史证据。

### 示例与验证方式

假设接口 A 与 B 共享认证机制，计划是在 B 上复核 A 已确认问题的触发条件。后来在对应身份与环境下观察到 B 使用另一套机制，原触发前提不成立。

系统保留这条反证，定位依赖共享认证假设的计划，交给 Planner 重新评估。它只能说明复用 A 的测试依据需要修订，不能据此断言 B 没有其他问题。

验证时至少比较原实现、完成可靠性加固的实现、再增加可证伪计划的实现，避免把工程修复的收益误记到新机制上。重点观察错误假设被推翻后仍重复执行的次数、错误结论向后传播的情况、重新规划成本，以及最终有效产出。

持久化、事务和证据追溯属于成熟工程方法的应用；可证伪计划是相对 ARTEX 的演进设想，也不据此主张行业首创。

## 建议实施顺序与验收

| 顺序 | 工作范围 | 关键验收场景 |
| --- | --- | --- |
| M0 最先 | 轨迹审计、口径、固定案例与配置基线 | 错误可定位；数据不足有明确标记，不虚报比例 |
| M1 基础加固 | 完成旁路保护、图事务与不变量、规划引用 schema 和恢复 | 写入故障不误报成功；重建后计划与依据可恢复，迟到写入被拒 |
| M2 主架构 | 公共观察、谓词、基线、HTTP 通道，四道门、日志与分级呈现 | 以 R05 公共检查和 R02 只读差分贯通执行；前提漂移可复核 |
| M3 能力扩展 | R02 扩展、R03 可达性、R01 复核与 R06 复测接入 | 有效状态可重复到达，依据失效不错误续派，约简保留证明关系 |
| M4 分别晋级 | 有来源规则下的业务反例、各路线跨轮能力，再验证 R04 | 每项收益有独立对照；能力链不靠未知连接成立 |
| 条件分支 | 对完整 M2 主线的残余调度问题评估独立控制器 | 满足架构文档的准入条件，再证明相对门化 Planner 的增量 |
| 按部署需求 | 远程执行租约及针对性覆盖矩阵 | 有明确场景，能处理执行归属、迟到结果和条件差异 |

详细版本依赖以[路线规划](创新路线/README.md)为准。评估区分原实现、M1 加固、门化 Planner 与条件性独立控制器四组；新控制器不能把前三组已经获得的收益重复计算，也不以六条路线全部完成为启动要求。
